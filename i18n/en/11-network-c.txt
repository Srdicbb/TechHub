HTTPS and the TLS handshake
@b26eecba05
HTTPS is HTTP over **TLS**. Before the first request, in the **handshake**, the client and server agree on algorithms, the server proves its identity with a **certificate** signed by an issuer the client trusts (a CA), and both sides derive a shared **session key** that encrypts everything afterwards. TLS 1.3 needs one RTT for that, TLS 1.2 two, and HTTP/3 merges the TCP and TLS steps into one.
@0e7fa95d2f
A certificate binds a domain name to a public key. The client checks the chain up to a CA it trusts, the validity period and whether the name matches the host.
@70827444b1
The key exchange (ECDHE) produces the same secret key on both sides without it ever traveling over the network. A later theft of the server's key does not reveal old sessions (forward secrecy).
@84a42ab107
When resuming a session, the client can send the request in its very first message (0-RTT, TLS 1.3 and QUIC). Such data can be replayed, so it may be used only for idempotent requests.
@9dd7769311
TLS is usually terminated at the edge (load balancer, Application Gateway, ingress); inside, traffic is re-encrypted when needed or uses mTLS, where the client also has a certificate.
@1223e15261
**HSTS** tells the browser that the domain is always opened over HTTPS, so not even the first request goes unencrypted.
