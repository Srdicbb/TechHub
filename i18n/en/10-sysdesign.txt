Vertical and horizontal scaling
@e3ab19f8eb
**Vertical** scaling means a bigger machine: more cores and memory for the same instance. **Horizontal** means more copies of the same application behind a load balancer. Vertical is the simplest, but it has a ceiling and usually needs a restart. Horizontal has no practical ceiling and survives the loss of a machine, but the application must be stateless.
@4dd1622b9e
Vertical needs no code changes, but the biggest machine is the ceiling, the price grows faster than the power, and a single instance is still a single point of failure.
@2cd6cfd458
Horizontal: session, files and cache have to move out of the process (Redis, blob storage, the database), because the same user's next request may land on another instance.
@d05a03467b
An autoscaler adds instances based on a metric: desired = ceil(current × current metric / target). With 4 instances at 90% CPU and a 60% target it asks for 6.
@a5b38da6ca
A new instance needs time to start and warm up (JIT, cache, connections), so a spike that lasts seconds has to be absorbed by spare capacity or a rate limiter.
@8299e12cca
The database is the hardest to scale: the application is easy to copy, the data is not.

@8b1aff51dd
Before drawing an architecture it pays to estimate the load roughly: how many requests per second, how much data and how many instances. The goal is not an exact number but the order of magnitude, to see whether the problem is 100 or 100,000 requests per second.
@4e59b7cd6e

@f245b2619c

Monolith or microservices
@d676b90dcd
A **monolith** is one application that is built, deployed and scaled as a whole. It is simple to develop, test and debug: calls between modules are ordinary method calls, and a transaction across the whole database comes for free. **Microservices** split the system into services that are deployed and scaled independently, each with its own database: a team changes its service without waiting for the others, a loaded part scales on its own, and the failure of one service does not bring down the whole system. The price is the network between services (latency, partial failures), data without a shared transaction, and much more operational work, because every service needs its own deployment, monitoring and tracing. A good default start is a **modular monolith** with clear module boundaries, which is split later where it really hurts.
@df25db558d
Switch the architecture to **Microservices** and raise the load to 15,000 req/s: only Catalog is overloaded. When it fails, Orders and Payments keep working, and the autoscaler adds instances mostly to Catalog. A monolith under the same load fails as a whole.
@ac3a77c4fb
Firewall and WAF
@1f00ae0ce9
The first filter at the entrance. A **network firewall** (L3/L4) lets through only allowed addresses, ports and protocols. A **WAF** (L7) reads HTTP requests and blocks known attacks: SQL injection, XSS, malicious bots. In front of everything is **DDoS protection** at the network edge, which absorbs huge traffic before it reaches your servers.
@8d23ac92cf
Least privilege: from outside only port 443 at the edge is open, and the database and internal services have no public address (private network, NSG, security groups).
@d4f8789fbd
A WAF works by rules (e.g. the OWASP Core Rule Set) and can also block valid requests, so it is introduced in detection mode first and only then in blocking mode.
@5e6375ce18
TLS is usually terminated at the edge (Front Door, Application Gateway, ingress), and inside it is re-encrypted when needed (mTLS between services).
@d876dd39ee
In Azure: NSG and Azure Firewall for the network, a WAF on Front Door or Application Gateway, DDoS Protection for network attacks.
@abc938ae7c
A firewall does not replace security in the application: authentication, authorization and input validation are still required.
@ba6cd0f4f3
Purple orbs are malicious requests. The firewall stops them before they consume any of the application's capacity.
@8e45de504d
A single entry point for clients in front of several services. The gateway routes a request by path or host (`/katalog` goes to the Catalog service) and takes over shared work: authentication, rate limiting, TLS, response caching, versioning and combining several calls into one.
@02aac66af0
The client does not know where the services live or how many there are: the gateway hides the internal topology and can change it without changes on the clients.
@02fdc2d079
**BFF** (backend for frontend): a separate gateway for the web and for the mobile app, each with responses tailored to its client.
@b35ed64330
The gateway must not become a new monolith: business logic stays in the services, and the gateway does only general things.
@6a07e9a931
Every request passes through it, so it has to be fast and redundant.
@2e95f81f3d
.NET: YARP as a reverse proxy in code; Azure API Management, Kong or NGINX as ready-made solutions.

Rate limiting and load shedding
@9e2a83416e
A rate limiter caps how many requests a client or the whole system may send per unit of time. The excess is rejected immediately with `429 Too Many Requests` instead of entering the system and bringing it down. It is better to reject some requests than to fail for everyone.
@5a93e8d173
Algorithms: **token bucket** (allows short bursts), fixed window, sliding window and concurrency limit. In detail in the topic [[rate-limiting]].
@8a5655eedf
A limit per user or API key protects against one noisy client; a global limit protects the system from total overload.
@5cd3eb612a
With several gateway instances the counter has to be shared (Redis), or the limit is divided by the number of instances.
@0dadd2714d
**Load shedding** is a related idea: a service itself drops work when it is full (the queue is too long, latency too high) instead of accepting until it fails.
@40476b5549
The client should respect `Retry-After` and retry with backoff and jitter, otherwise the retries create a new wave.

Caching and CDN
@32296b7ddc
A cache keeps the result of expensive work closer to whoever asks for it. Every hit is one database query less: with 90% hits the database sees ten times fewer queries. Caches exist at several levels, from the browser and CDN to process memory and Redis.
@54db555a82
A **CDN** keeps static files and public responses on servers close to the users: lower latency and less traffic to your system.
@9935964c5e
A **local cache** (`IMemoryCache`) is the fastest, but every instance has its own copy; a **distributed** one (Redis) is shared by all instances and survives restarts.
@36b026facf
**Cache-aside**: read from the cache, on a miss read from the database and write into the cache. The most common pattern; details in [[cache-aside]].
@151384b5c3
The hardest part is invalidation: a TTL limits how long data may be stale, and deleting the key on write shortens that window.
@dd1ad079fa
A cold cache after a restart or after a popular key expires sends everything to the database at once: that is a [[stampede]].

Scaling the database
@1443f6e847
The database is usually the first bottleneck, because the application is easy to copy and the data is not. The order is roughly: good indexes and queries, caching, a bigger machine, read replicas, and only then splitting the data across several databases (sharding).
@d123f4bcfa
**Indexes and queries** are the cheapest optimization: one query without an index can eat the CPU of the whole database. Watch out for [[n-plus-one]] too.
@f1afdf4f58
**Connection pool**: opening a connection is expensive, and the database accepts a limited number. With 20 instances × 100 connections it is easy to exceed the database limit.
@f019252e83
**Read replicas** take over reads. Replication is usually asynchronous, so a replica lags (replication lag) and the user may not see their own write right away.
@620c155aef
**Sharding** splits data by a key (e.g. tenant or user) across several databases. It scales writes too, but queries and transactions across several shards become hard, and a bad key creates a hot shard.
@8f73358050
**CQRS** separates the write model from the read model, which can live in another database or in a search engine.
@5bc24930b7
SQL for relations, transactions and ad hoc queries; NoSQL (Cosmos DB, MongoDB) for key-based access, huge volume and global distribution. See also [[cap]].
@5bba15a542
The bar above the database is its load. In the monolith there is one database for everything, and in microservices every service has its own, so an overloaded Catalog database does not slow down Payments.
@8f2fdb531f
Queues and asynchronous processing
@b4902b2295
Not everything has to finish while the user waits. Slow or risky work (sending an email, processing a payment, a report) goes into a queue, and the API returns `202 Accepted` right away. The queue absorbs bursts: the producer writes fast and the consumers process at their own pace.
@88552dc995
A queue decouples services in time: if a consumer fails, messages wait in the queue instead of getting lost.
@2fc53d1796
Consumers scale by queue length (KEDA), independently of the API.
@a092d9aafa
Delivery is usually at-least-once, so processing must be idempotent: the same message twice must not charge twice.
@ff7cbf0f6e
Writing to the database and sending the message are tied together by the [[outbox]]; otherwise one of the two may be missing.
@f14fe0311a
A queue when one consumer does the work, a topic when several services need the same event, Kafka when you need a log that can be read again.

Fault tolerance
@837201a319
In a distributed system something is always broken: an instance, the network, a dependency. The goal is for the failure of one part to stay local instead of spreading to the whole system as a cascading failure.
@efdd862a98
**No single point of failure**: at least two instances of everything, in different availability zones (N+1).
@d399efa831
A **timeout** on every call to a dependency; without it a slow service ties up threads and connections until everything stops.
@b358393a40
**Retry** with exponential backoff and jitter, only for transient errors and idempotent operations.
@a34f7ff708
A **circuit breaker** stops calling a failing dependency and gives it time to recover; details in [[circuit-breaker]].
@31447be770
**Bulkhead**: separate thread and connection pools per dependency, so a slow dependency does not eat the resources of all the others.
@1b079fd1bd
**Graceful degradation**: when recommendations do not work, show the page without them instead of an error.
@2dcc4dcc60
