Process and thread
@480b5e4a3a
A process is a program with its own address space. A thread is a flow of execution inside a process: it has its own stack and registers, and it shares the heap and static fields with all other threads of that process.
@fe9323bbab
Every thread has **its own stack**: local variables and the call chain. Objects on the **heap** and static fields are shared by all threads of the process.
@5518f8fee6
That is why a local variable is safe by itself, while a shared object needs synchronization as soon as some thread modifies it.
@e5a414e3cd
A new thread is not free: a kernel object, a reserved stack (usually about 1 MB) and the cost of switching. That is why the ThreadPool exists.
@377eaa605e
A foreground thread keeps the process alive until it finishes. A background thread (and every pool thread) is stopped when the process shuts down.
@b01e996726
An unhandled exception in any thread (`new Thread`, a timer callback) crashes the whole process. An exception in a `Task` is stored in the task and surfaces at `await`.

Race condition
@ed5af60f34
When two threads **read, modify, write** the same variable at the same time, one overwrites the other's result. `count++` is not one operation but three.
@450621689c
`count++` is a read, an addition and a write. Between those three steps another thread can write its own value.
@752479fb8a
The outcome depends on the thread schedule, so the bug shows up rarely and unpredictably, usually only under load.
@9324009799
`lock` makes the whole block indivisible for all threads that use the same lock object.
@7c8837f4d1
`Interlocked.Increment` does the same for a single variable, atomically in the processor and without locking.
@ff980000ea
The best protection is state that is not shared: immutable objects, messages, local copies merged at the end.

Semaphores: SemaphoreSlim and Mutex
@2cec9bfa15
A semaphore is a gate with N tokens: a thread takes a token on entry and returns it on exit, so there are at most N threads inside. `SemaphoreSlim` is lightweight and can be awaited asynchronously, while `Semaphore` and `Mutex` also work across processes.
@8daf0607e8
A thread takes a token on entry (`Wait`) and returns it on exit (`Release`). When there are no tokens, it waits.
@3cc84ffe84
Typical uses: at most N simultaneous API calls, a limited number of connections, at most N jobs in progress.
@09b6334f1a
`WaitAsync` waits without blocking the thread, so `SemaphoreSlim(1, 1)` is the usual async "lock" (`await` is not allowed inside a `lock` block).
@e3a041e3c4
A semaphore has no owner: another thread can return the token. A `Mutex` has an owner and works across processes, e.g. for a single instance of an application.
@f1d2329a3c
