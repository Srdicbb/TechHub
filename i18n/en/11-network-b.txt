HTTP: request, response and versions
@d27f6bfcb8
HTTP is a request–response conversation: the client sends a **method**, a **path**, **headers** and, when needed, a body, and the server returns a **status**, headers and a body. The message is the same in all versions; what changes is how it travels: HTTP/1.1 one request per connection at a time, HTTP/2 many streams over one TCP connection, HTTP/3 the same over QUIC on UDP.
@0efd70c473
Status codes by group: **2xx** success, **3xx** redirect, **4xx** client error (400, 401, 403, 404, 409, 429), **5xx** server error (500, 502, 503, 504).
@602e9ea1d6
Headers carry everything else: `Content-Type`, `Authorization`, `Cache-Control`, `ETag`, `Accept-Encoding`.
@61d9b2f230
HTTP/1.1 keeps the connection open (keep-alive), but only one request at a time goes over a connection, so the browser opens up to 6 connections per host.
@45ce41b560
HTTP/2 sends all requests at once over one connection (multiplexing) and compresses headers. But one lost TCP packet stops all streams (head-of-line blocking).
@3825e7f29d
HTTP/3 runs over QUIC: streams are independent, so a loss stops only its own stream, and the connection opens in one RTT.
@d4d45fdbae

HTTP methods and idempotency
@7137ecde2f
The method says what the request does with the resource. Two properties decide whether it may be repeated: a **safe** method does not change state (GET, HEAD), and an **idempotent** one leaves the same state no matter how many times it is called (GET, PUT, DELETE). POST is not idempotent: a repeated POST creates a new resource.
@eaba49040a
**GET** reads, **POST** creates a new resource or triggers an action, **PUT** sets the whole resource, **PATCH** changes part of it, **DELETE** deletes it.
@779f1cca05
Idempotency is about state, not the response: the second DELETE returns 404, but the resource is still gone.
@c83048717f
The network can lose the response after successful processing. The client then does not know whether the server did the work, so it retries; that is why automatic retries are allowed only on idempotent operations.
@a49a34b805
A POST is made idempotent with a key: the client sends an `Idempotency-Key`, the server stores the key and the result, and a repeated request gets the same response (that is how Stripe and most payment APIs work).
@a5eb84c065
PATCH may or may not be idempotent: "set the status to paid" is, "increase the quantity by 1" is not.
