Stack, heap and GC
@286c0977dd
Local variables and references live on the **stack** and disappear when the method ends. Objects live on the **heap**, and the garbage collector removes the ones that can no longer be reached; it splits the heap into generations, because most objects die young.
@a1974d7088
Value types (`int`, `struct`) as local variables live on the stack; reference types (`class`) are always on the heap, and only the reference is on the stack.
@610e869957
The GC starts from the roots (the stack, static fields, registers), marks all reachable objects and frees the rest.
@e783794fd5
Gen0 is collected often and fast. Survivors move to Gen1, then to Gen2, where collection is rare.
@9107df27ad
Objects of 85,000 bytes and more go to the **Large Object Heap** (LOH), which is collected with Gen2 and is not compacted by default.
@02f4b968fd
Boxing: when a value type goes into an `object`, a copy is created on the heap. In a loop that is needless garbage.

The ASP.NET Core pipeline
@3f060a1102
A request passes through the middleware components in the order they were registered, and the response goes back through the same components in reverse. Each one can do something before and after the next, or stop the chain.
@896fcaf87d
The order matters: `UseAuthentication` goes before `UseAuthorization`, and the exception handler at the very start.
@bf9e759cec
A middleware that does not call `next` stops the chain (short-circuit): that is how static files, CORS preflight and 401 work.
@14bd828cb0
Code after `await next()` runs on the way back: that is where durations are measured and the outcome is recorded.
@8b4ef77f11
An exception thrown deep in the chain travels back to the first middleware that catches it.
@0fe31dce55
`UseRouting` selects the endpoint early, so middleware after it (authorization, CORS) knows which endpoint will run.
